# 标注后台：完整项目功能清单

上一份 [01-fastapi-learning-path.md](./01-fastapi-learning-path.md) 回答「先按什么顺序学、每步写什么」。这份回答「一个能上线的标注后台管理系统，功能要齐到什么程度」。

两份文档的关系：

- 学习路径：垂直切片，保证每一天都有能跑的接口，走完是「生产级底座 + 一个资源」。
- 完整项目：水平清单，避免上线前才发现缺用户、缺导出、缺任务流。

状态标记：

| 标记 | 含义 |
|---|---|
| 已覆盖 | 学习路径 0–16 步某一步会做到最小可用 |
| 完整项目 | 学完 0–16 步之后再做，交付一个真产品需要 |
| 按需 | 业务真出现再做，不是后台标配 |

「已覆盖」不等于「做完了」。学习路径做的是**能上线的最小实现**，产品化程度靠这份清单往上补。

## 2. 身份、租户、权限

这是管理系统的骨架。学习路径用假用户把缝挖好，第 14 步接 Logto 把缝填实。

**认证不是本项目的工作量**：账号、密码、找回密码、MFA、社交登录都在 Logto。这一节里大半行的状态是「不做（Logto）」——它们仍然列在这里，因为「谁负责」这件事必须写下来，否则半年后会有人来问「我们为什么没有改密码接口」。

### 2.1 认证

| 功能 | 说明 | 状态 |
|---|---|---|
| CurrentUser 上下文 | 下层只认 user_id / tenant_id / roles | 已覆盖（第 6 步） |
| 假用户后门可关 | 非 local 环境 header 身份直接 401 | 已覆盖（第 6、16 步） |
| 登录 / 注册 | Logto 托管，前端跑它的 SDK。后端没有登录接口 | 不做（Logto） |
| 密码存储与哈希 | Logto 承担。本地库没有密码列 | 不做（Logto） |
| 登录失败不泄露账号存在性 | 同上，Logto 的登录页负责 | 不做（Logto） |
| 改密码 / 重置密码 / 登出 / 刷新令牌 | Logto + 前端 SDK，后端不参与 | 不做（Logto） |
| 验证码 / 2FA / SSO / 社交登录 | Logto 控制台里的开关，不是开发任务 | 配置即可（Logto） |
| Token 校验 | JWKS 验签 + `iss` / `aud` / `exp`，算法白名单 | 已覆盖（第 14 步） |
| Logto 用户 → 本地用户映射 | `users.logto_user_id` 唯一，JIT 建人且幂等 | 已覆盖（第 10、14 步） |
| `/me` | 当前用户资料 | 已覆盖（第 10 步） |
| 用户变更同步 | Logto 那边改邮箱、停用、删号，本地那行怎么跟上（webhook `User.Created` / `User.Data.Updated`，或每次登录刷新快照） | 完整项目 |
| 停用即时生效 | 本地验签的代价是 token 没过期就还能用。要即时生效得在依赖里查本地状态位，或把 token 调短 | 完整项目 |
| 登录限流 / 账号锁定 | 爆破归 Logto；你这边限的是拿到 token 之后的滥刷 | 已覆盖 IP 限流（第 16 步） |
| Logto organizations 多租户 | `logto_org_id → tenant_id` 映射表，从组织 token 的 `organization_id` 翻译 | 完整项目 |
| Management API 反向操作 | 后台建人时顺手在 Logto 建账号并发邀请（M2M client_credentials 拿 token） | 完整项目 |

## 8. 建议的产品模块切分

完整项目按模块开发时，用这个切，不要按「再写一个 CRUD」切。

```text
平台
  配置 / 信封 / 错误 / 日志 / 审计 / 健康检查 / 文件

身份
  Logto 接入 / 用户映射 / 租户 / 角色 / Casbin

系统管理
  字典 / 参数 / 操作日志 / 登录日志 / 导出

标注核心
  项目 / 标签体系 / 数据集 / 样本
  任务 / 分配 / 标注结果 / 质检

标注增值
  预标注 / 统计看板 / 异步导入导出 / 协同
```

依赖顺序：平台 → 身份 → 系统管理 → 标注核心 → 标注增值。
学习路径走完，约等于「平台完整 + 身份最小集 + 一个项目 CRUD」。其余都是这份清单里的「完整项目」。

## 9. 完整项目的推荐实现顺序

学完 0–16 步之后，如果要把仓库做成可交付后台，按这个顺序补，而不是按兴趣跳：

1. **把身份接入做完整**：Logto webhook 同步用户变更、停用即时生效（本地状态位）、后台建人时用 Management API 在 Logto 建账号并发邀请、登录日志。注意这一条比原来的「自己做登录产品化」小得多——刷新令牌、登出、改密码都不在你这边。
2. **权限可运营**：Casbin 策略入库 + 变更即时生效、角色管理接口、用户多角色、前端菜单树。
3. **项目成员 + 标签体系**：没有标签体系，后面的任务是空的。
4. **数据集 + 对象存储 + 导入队列**：标注后台从此才像标注后台。这一步同时引入 Redis 和 worker。
5. **任务状态机 + 分配 + 提交 + 质检**：核心闭环。并发控制在这里必须做对。
6. **导出 + 看板**：给项目经理用，导出走队列。
7. **管理台收尾**：恢复软删、操作日志查询、字典、系统参数、导出 Excel。
8. **运维补齐**：指标告警、备份恢复演练、密钥托管、审计归档、依赖扫描。

预标注、协同、邮件邀请，都放在闭环能跑之后。SSO 和 2FA 不在这个排序里——它们已经变成 Logto 控制台里的开关，不占开发时间。

注意第 4 步一旦引入队列，就多了一个进程形态（worker），部署、日志、配置、迁移都要跟着改一遍——这不是「加个库」那么小，安排时间时按一个大步骤算。

## 10. 刻意不放进完整项目默认范围

这些常见，但不该变成「标注后台必须有」：

- GraphQL / tRPC（REST + OpenAPI 足够）
- 微服务拆分（先单体）
- 每租户独立数据库（先共享库 + tenant_id）
- 数据库行级安全策略 RLS（应用层租户条件 + 测试已经够）
- 计费 / Stripe
- 自建社交登录 / SSO / 密码体系（要用就在 Logto 里开，不要往后端加登录接口）
- 完整 APM 平台（先有指标和日志）
- 自研工作流引擎
- k8s / Helm / 金丝雀（先有一个能跑的镜像）

需要时再开，不要写进第一版范围。
